自傳

從製程現場到 MES 系統開發，我在半導體路線上走了七年以上。先做過晶圓測試製程的異常追查與良率工作，累積五十多場失效分析——每一場都是從現象列假設、做實驗、驗證、收斂成 SOP 與防呆。後來轉任 MES IT，改用 C# 與 .NET Core 開發生產管控系統，從需求訪談、規格制定、測試到上線教育訓練都走過。長期和產線工程單位合作，所以我寫出來的東西，現場才會真的用。

這段經歷讓我養成一個習慣：任何流程上線，先想它會怎麼壞。系統該怎麼兜錯、錯誤該有紀錄、有流程，而不是只求把規格跑完。這個思維後來我帶到 AI agent 的自學上。

課餘時間我動手寫過 MiniGPT（自學實作，loss 5.06 收斂到 0.017）與 LangGraph + RAG 小型專案（char n-gram 檢索、faiss 向量儲存、FastAPI 介面，加 LLM-as-judge 評測與人工 review）。我放在「自學實作」的位置，因為我知道這些還不是可直接上線的成熟系統，也清楚目前的缺口在哪——多 agent 協作、正式 MLOps、雲端部署都還在學。

碰到 AI agent 系統時，我會先問：這個系統最終為誰解決什麼現場問題。一個能寫程式、能檢索回應的 agent，要怎麼設計才不會在訊息模糊或工具回應不完整時亂掉。我的答案傾向於把越需要穩定可靠的環節放在明確的契約與驗證下，讓 agent 在能力範圍內做事，超出範圍時有明確的處理方式。這想法來自製程與 MES 學到的教訓，也來自自學 AI 時看到的失效模式。

我適合的方向，是把半導體製造領域的理解、MES 與系統開發經歷，與正在累積的 AI agent 開發能力結合起來。對內部流程做智慧輔助、或為使用者設計能與 LLM 互動的工具，我能帶著對使用者工作情境的理解去設計，而不只在模型接口上調一調。我也知道自己的節奏：把問題講清楚再動手，設計階段先列可能的 failure 點。

我投這份，是因為半導體場景的 AI 應用與 LLM 系統，需要懂現場的人——七年製程經歷加上 MES IT 實作，以及我對 AI 工具鏈的自學實作，與這條路最匹配。我希望未來能在穩定可上線的 AI agent 系統這條路上繼續往前走。
